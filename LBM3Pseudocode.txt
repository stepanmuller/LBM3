Esotwist streaming and grid connectivity
	- On unstructured grid this only requires 2 arrays of full length: jPlus, kPlus. 
	These store the neighbour cell index in the jPlus and kPlus directions. For the rest of the cube, we do
	jkPlus = jPlus[kPlus], iPlus = cell+1, ijPlus = jPlus + 1, ikPlus = kPlus + 1, ijkPlus = jkPlus + 1, for indexes >=N we wrap to zero.
	If jPlus cell doesnt exist in this position, we continue travelling in this direction and wrap around borders periodically till we find a valid cell.
	Same for kPlus. This way all cells have uniquely assigned neighbours.
	On the border, doing jPlus[kPlus] could result in wrong geometry, but we are keeping one layer of wall cells which dont need correct neighbours.
	All fluid cells will have correct geometric neighbours this way.
	
Interpolation between grid levels
	- this is already working from previously so we dont go into much detail in this document
	- we store list of coarse interface cells and their bottom left fine children. The remaining 7 children inside one coarse cell are found thanks to jPlus, kPlus.
	- the interpolation also requires negative neighbours -> we store jMinus, kMinus, but only for the interface. So these arrays will have the same length as
	the interface which is minimal compared to full N.

compressed IJK
- The former approach to store geometry of the unstructured grid was iArray, jArray, kArray that held spatial indexes of cells.
The memory footprint can be decreased from 3N to N:
Only save i, j, k explicitly for the first-in-continuous-row cell. Such iArray, jArray, kArray is by an order shorter.
Then allocate a fully long array IJKShifter, so that
shift = IJKShifter[cell]
if shift >= 0:
	i = iArray[shift], j, k...
else:

	i = iArray[firstInRow] - shift

Non reflective boundary conditions
	Store a list of boundary cells. Also store one equally long float array which works as BC memory.
	This is enough to implement some kind of non reflecting boundary conditions.
	Loop through all boundary cells, get their i, j, k
	From some acustic or impedance relations, must be local, and from the BC memory, determine a non reflecting value of rho
	that should be prescribed for the cell. This only works for face cells 
	(for corner or edge cells, we will apply a strict dirichlet	and dont try to calculate any non reflective values)
	From i, j, k, via a user function determine whether this cell is dirichletU or dirichletRho
	get the dirichlet values and a reflectivity value. The reflectivity says how much can the applied rho differ from the non reflecting rho.
	non reflectivity set to 1 means that a strict dirichlet will be applied.
	we do rhoFinal = clamp ( rhoDirichlet, rhoNonReflecting-nonReflectivity, rhoNonReflecting+nonReflectivity)
	Based on this relation and also the relation of normal velocity and density in LBM, we solve rho and U for all cells 
	(for both dirichletU and dirichletRho) and proceed to apply the already working MBBC (moment based boundary conditions)
	Only write the unknown distributions.

How to handle stationary walls or moving walls with axial symmetry (rotor hub) where cells dont change state
	Interpolated bounceback by Weifeng Zhao, Wen-An Yong, 2017. Set l = gamma which also agrees with the Geier's version.
	First, for all cells we need to remember whether they are a wall themselves, or if they have an adjacent wall nearby,
	or if they are purely fluid. For this we allocate an array wallMap of full length N.
	wallMap[cell] = -2 => this itself is a wall cell (we are keeping one layer of wall cells next to the fluid region)
	wallMap[cell] = -1 => this is a free fluid cell (there is no wall nearby)
	wallMap[cell] >= 0 -> this is a fluid cell with one or more wall neighbours. The int stores order of this particular wall adjacent cell.
	To apply the interpolated BB by Zhao, Yong, we need to identify which of the neighbours are wall and their link lenghts. 
	I will pack 26 link existences and distances into 128 bits. This can be either 4*uint32 or one 128bit CUDA vector (need to check if TNL works with this)
	Then I treat it as 4 uint32 and assign 7, 7, 7, 5 links to them. 
	Each link has a code from 0 to 22 inclusive. I unpack the link codes as following:
		for i in 7 links:
			uint32_t linkCode[i] = bitPackedValue % 23u;
			bitPackedValue /= 23u;
		if linkCode[i] == 0 -> link doesnt exist (there is no wall in this direction)
		else -> map integer interval <1, 22> onto a float interval <0, 1>, this float is the resulting link distance.. 
		beware, maybe you want to represent link length 0.5 exactly so the interval should be shortened to <1, 21>
		also specify the edge cases 0 or 1! Do I allow those?
	There could be 2 more links stored, this means we can store two more numbers from <0, 22>. We can use the first link
	to store the wall code: as there may be multiple different bodies (multiple STLs), here we can store
	the index of the STL / body that is adjacent to us. We can send this index to the BC function, that way
	the BC function knows if it should return the rotor velocity (moving wall) or just zero (stationary wall).
	This also allows to calculate force on each body separately.
	In fact, it may be better to use the very first "link" to store the body index because we need to access this first.
	In addition, allocate 3 float arrays gx, gy, gz, these will store cummulative exerted forcing for each wall adjacent cell,
	we will write this every timestep.

How to handle rotating geometry
	For cells that are covered by a rotor, we enforce the rotor velocity via a forcing term.
	The rotor is stored by a supersampled voxelization stored in a block format that uses the fact
	that the rotor is sparse to save memory. Then on this voxelization we interpolate to find
	how much is a given cell overlapped by the rotor, which ranges from 0 (free fluid) to 1 (deep rotor).
	Struct Rotor will hold some stuff, importantly Bounds (if a point lands outside bounds we dont do any interpolation
	and set 0 immediately)
	The voxelization and interpolation goes like this:
	I have the finest LBM grid. I set the bounds with a little overlap and define a voxelizer grid inside it that is 2x finer than the finest LBM grid.
	Binary values are assigned to this grid (but I dont allocate this, I just use an efficient raymap to store this information)
	Next, define the actual interpolation grid. Beware that this interpolation grid is now collocated 
	(1/8 of points are shared with the LBM grid, this differs from grid refinement where no points are shared) 
	This grid also has 2x finer resolution than the finest LBM grid. For every of those interpolation cells, I sum the binary values of the
	voxelizer, note that the voxelizer points are in the corners of the interpolation cells. This gives a value from 0 to 8, which can be stored in 4 bits.
	I will code this into an int but also use the remaining bits to store the same information about 7 neighbour cells in the positive directions.
	This way, to get the interpolation values, all I need is to read a single int from the cell that is the closest to me in the negative directions.
	Because the rotor is going to be block-like (large blocks of zeros or ones), I will use a larger block structure to greatly save memory. 
	The large blocks will contain, lets say, 4x4x4 of those interpolation cells. If every single value there is zero, this block receives a -1. If at least one values is > 0, 
	this positive block will receive an integer which tells the order of this positive block. Then we allocate a second array which contains sectors of 64 ints, those are the "in detail" values and
	the only place where I actually start storing the interpolated values (I can get all the way here using just by browsing the rayMap).
	They are ordered within the block just like everything else, k/z changes the slowest. Load the needed in detail int from here.
	How to find volumetric fraction of a cell: 
		1) project its position into the rotor frame
		2) if not within bounds, return 0
		3) identify which large block we are in. Read blockMap[block], if -2 return 0, if -1 return 1. Else, read interpolationArray[64*blockMap[block] + orderWithinBlock]
		This int is bit packed as discussed previously, unpack it and convert the values to floats, inside this cube do trilinear interpolation. Return result.
	In addition to the interpolation array, I will allocate 3 more float arrays of the same length: gx, gy, gz. This will be used to store the exerted forcing,
	but in frame of reference of the rotor. Storing this in the rotor frame is the simplest way I found to avoid having large forcing arrays for every cell. This way,
	those arrays are as sparse as the rotor is. The forcing must be transformed into the rotor frame! This is because I not only later need to calculate sum
	of gx, gy, gz but also torque, and so I need to keep correct orientation of the vector, as the arm will be calculated in the rotor frame. Note that this introduces
	tiny errors: we cannot remember position of the actual LBM cell where the forcing was imposed, and so the arm will be approximated as just the center of the interpolation
	cell where the interpolation happened. In average, those errors should cancel out, and also they are very small 
	(if cell is 1mm and rotor is 100mm thats only 1% and that would be very coarse)
	Note that we are only writing the forcing if the cell doesnt belong to interface overlap! This prevents excessive forcing evaluation on the interfaces
